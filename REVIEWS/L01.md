## Runtime behavior

`cargo run -p l01-runtime` output:

```
Task ready done with return "Always ready!"
Task 0 finished.

Task instant yield by delaying negative done
Task 2 finished.

Task yield done
Task 1 finished.

Task Joining Ready and delay 1s done
Task 4 finished.

Task delaying 1s done
```

Key correctness observations:

- **Interleaving proven**: tasks finish in `0, 2, 1, 4, 3` order (not spawn order `0, 1, 2, 3, 4`). Task 2 (past-deadline Delay) races ahead of Task 1 (Yield) because Yield needs a re-poll cycle after its initial Pending. Task 4 (Join2) completes before Task 3 (raw 1s Delay) — very close in time; scheduling determines order.
- **Concurrency proven**: total wall time is **1s**, not 2s. Task 3 (1s Delay) and Task 4 (Join2 of Ready + 1s Delay) run *in parallel* — their timer threads fire independently. Sequential polling would give 2s. This is the critical proof point for L01.
- **Executor terminates cleanly** when `task_map` empties.
- **Past-deadline Delay fast-path fires** (Task 2 finishes immediately, no timer thread wait).

## Senior-eye pass

Architecture is right:
- Executor / Task / TaskWaker / Shared split matches the shape of every real runtime (Tokio uses the same three-part decomposition).
- Waker cached on Task — one Arc allocation per task lifetime, not per poll.
- `Shared` bundles the cross-thread state (ready queue + executor Thread handle); `Executor` keeps executor-exclusive state.
- Wake path: reactor → `enqueue` → lock, push_back, unpark. Correct, race-free with executor's park.
- Delay uses copy-out-then-spawn pattern (`let until = self.until; let waker = cx.waker().clone();`) — no `self` reference bleeds into the 'static timer closure.
- Deadline fast-path in `Delay::poll` correctly handles past deadlines without spawning a thread.
- `saturating_duration_since` inside the timer closure eliminates the race panic.
- Executor's `run` guard scope is tight (`let id = { …lock…pop_front… };`) — no lock held across `poll_one`. Reactors can push freely during polling.
- Yield's synchronous `wake_by_ref` + Pending pattern is correct — unpark's single-slot token makes wake-then-Pending and Pending-then-wake both work.
- Join2 correctly uses pin-project-lite; children are `#[pin]`, output slots are not. The two-slot pattern (`Option<T>` per child) doubles as the "done?" flag.

## Nice-to-have (recommended cleanup, not graduation-blocking)

### N1 — Drop the `T: Clone` bound on `Ready<T>`'s Future impl

`src/main.rs:135`:

```rust
impl<T: Clone> Future for Ready<T> {   // ← Clone bound is unnecessary
```

`Option::take()` already returns owned `T` — no cloning happens. This bound needlessly rejects `Ready<TcpStream>`, `Ready<Box<dyn Trait>>`, `Ready<File>`, etc. Change to:

```rust
impl<T> Future for Ready<T> {
```

Std's `std::future::Ready<T>` matches this — no Clone bound.

### N5 — Join2 design suggestions (not required)

Two possible refinements:

- **Store futures directly, not `Pin<Box<dyn Future>>`.** Since Join2 is already generic over `A` and `B`, you can hold the concrete futures without erasure:
  ```rust
  pin_project! {
      struct Join2<A: Future, B: Future> {
          #[pin] fut1: A,
          #[pin] fut2: B,
          fut1_out: Option<A::Output>,
          fut2_out: Option<B::Output>,
      }
  }
  ```
  No `Box::pin` in `new`. No heap allocation for children. Compiler monomorphizes per (A, B) pair. Standard shape used by `futures::future::Join`.
- **Return `(A, B)` from Join2**, not `()`. Currently the output values are discarded. Making the return `(A, B)` (via `take()` on both `Option`s at Ready time) makes Join2 reusable in real code where you actually want the joined results.

Neither is required; your L01 use case (await until both complete, discard values) works with the current `Output = ()` shape.
